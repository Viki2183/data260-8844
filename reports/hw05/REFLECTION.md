# HW5 Reflection

I reviewed the blocked password-search run from agent_runs.jsonl. The user request was “Search for password records.” The agent started with step 1 and selected the search tool with the input query “password” and limit 5. Before the database operation ran, the safety_check function examined the query. Because “password” is a credential-like term, the safety rule blocked the request. The tool returned the shared envelope with ok set to false, data set to null, and the error “safety rule blocked credential-like search.” The agent then received that result and stopped at step 2 with the stop reason model_final. Its final response explained that the request was blocked by the safety rule. The run was recorded in agent_runs.jsonl with the original input, selected tool, inputs, returned envelope, final answer, and stop reason.

This run shows why safety must be enforced in the tool layer instead of relying only on the model. Even if the model chooses a tool correctly, the tool gateway can still prevent a sensitive request from reaching the database. The shared response envelope makes the blocked result predictable for the agent and automated tests. The offline safety test reproduced both an allowed package search and a blocked credential-like search. I also verified the maximum-step limit with a MockModel that continuously requested searches. That test stopped with max_steps instead of looping forever. These checks made the agent behavior more controlled, observable, and easier to debug.
